Activité 1 (SIO1) : maquette d'un réseau d'entreprise virtualisé

Contexte

Reproduire en laboratoire le réseau d'une petite entreprise, entièrement en machines virtuelles, pour s'entraîner à l'installation, à la configuration et à la sécurisation d'une infrastructure.

Environnement

  • Pare-feu pfSense et routeur (Routeur 1) pour relier et filtrer les réseaux.
  • Serveurs : Windows Server 2019 et deux serveurs supplémentaires (passfrw et srvlan1).
  • Postes clients Windows 10, Windows et Linux.
  • Machines modèles (MasterWIN10, MasterWIN19) pour cloner rapidement de nouveaux postes.

Ce que j'ai fait

  • Création et paramétrage des machines virtuelles à partir de modèles.
  • Installation et configuration du pare-feu pfSense, du routeur et des serveurs.
  • Mise en réseau des postes Windows et Linux et tests de connectivité entre eux.

Outils

Virtualisation de postes de travail, pfSense, Windows Server 2019, Windows 10, Linux.

Cluster Proxmox à haute disponibilité

Contexte

Construire une infrastructure virtualisée capable de redémarrer automatiquement une VM sur un autre serveur en cas de panne.

Ce que j'ai fait

  • Cluster Proxmox VE à 2 nœuds (pv1, pv2) en réseau bridgé sur un même sous-réseau.
  • Correction des erreurs pve-cluster, des certificats et de corosync.conf (noms de nœuds en double).
  • Serveur NFS partagé pour stocker les disques de la VM, puis déplacé sur pv2.
  • Script ha-watchdog.sh (ping de pv1 toutes les 30 s) en service systemd : force le quorum et relance la VM sur pv2.
  • VM Windows Server 2022 avec partage de fichiers SMB.

Difficultés et solutions

Perte de quorum quand un nœud tombe : résolue par le script de basculement. Test validé en éteignant pv1, la VM redémarre seule sur pv2.

Outils

Proxmox VE, Corosync, NFS, Bash, systemd, Windows Server 2022.

Supervision d'infrastructure avec Zabbix

Contexte

Superviser le cluster Proxmox et les hôtes du réseau. Objectif initial : Wazuh, abandonné faute de mémoire (Elasticsearch), après accord du tuteur, au profit de Zabbix, plus léger.

Ce que j'ai fait

  • Serveur Zabbix 7.0 LTS sur une VM Debian 12, base MariaDB.
  • Agents Zabbix sur les hôtes Linux et sur Windows Server.
  • Templates et items personnalisés : espace NFS, service SMB, processus corosync.
  • Triggers (hôte injoignable, CPU, disque, corosync) et notifications par e-mail.
  • Supervision de Proxmox via son API (token en lecture seule).
  • Semaine suivante : seuils affinés pour réduire les faux positifs, tableau de bord, nettoyage des hôtes obsolètes, test des alertes.

Difficultés et solutions

  • Conflit de dépendances et port 80 déjà utilisé : apt --fix-broken install et Apache sur le port 8080.
  • Agent inactif : le pare-feu UFW bloquait le port 10050.
  • Alertes en boucle sur le CPU au démarrage des VM : durée minimale de 5 min.

Outils

Zabbix 7.0, MariaDB, Apache, Debian 12, Wazuh (essai).

Dépannage réseau chez des clients

Contexte

Interventions sur site pour rétablir le réseau de plusieurs clients (concessionnaire, cabinet, entreprise).

Ce que j'ai fait

  • Remplacement d'un switch défaillant par un Cisco SG350-20 : recâblage étiqueté, VLAN existants reconfigurés, tests de tous les postes, bon d'intervention validé avec le client.
  • Concessionnaire : conflits IP réglés par des réservations DHCP, câble défectueux remplacé.
  • Cabinet : lenteurs et partages inaccessibles, DNS reconfiguré, pilotes mis à jour, règles pare-feu optimisées.

Difficulté et solution

Un poste sans adresse IP après le remplacement : renouvellement DHCP (ipconfig /renew).

Outils

Cisco SG350, ping, tracert, nslookup, DHCP, DNS.
